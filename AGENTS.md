# Appendix J — Comprehensive Quality Checklists

This appendix defines practical checklists that agents must use when the related work is in scope.

## Architecture Checklist

- Does the change preserve SEIS identity?
- Does the change strengthen Apple-first direction?
- Does the change strengthen Swift-first architecture?
- Does the change preserve or improve AI-native structure?
- Does the module have a clear owner?
- Does the module have a clear boundary?
- Does the module avoid unnecessary coupling?
- Does the module expose a stable interface?
- Does the change avoid framework churn?
- Does the change avoid duplicated responsibilities?
- Can this be reversed safely?
- Can a future contributor understand this without private context?
- Is an ADR required?
- Is documentation updated?

## Swift Checklist

- Is Swift used for real architectural value?
- Does the code compile in the intended package when tooling is available?
- Are models named clearly?
- Are enums used for finite states?
- Are Codable and Identifiable used only when useful?
- Are platform-specific APIs isolated from shared models?
- Are tests included when feasible?
- Does the package avoid unnecessary dependencies?
- Does Swift strengthen Apple-first direction?
- Is the Swift code more than symbolic language-stat manipulation?

## SwiftUI Checklist

- Does the component have a clear purpose?
- Does the component support accessibility labels?
- Does the component support dynamic type where appropriate?
- Does it avoid copying Apple apps?
- Does it follow SEIS visual identity?
- Does it use reusable tokens when available?
- Is state explicit?
- Are previews or examples useful when available?
- Does motion respect reduced-motion expectations?
- Is the component reusable across future native surfaces?

## AI Checklist

- Is demo mode clearly separated from live mode?
- Is there no fake provider claim?
- Are credentials isolated from frontend/public code?
- Is provider abstraction modular?
- Are error states documented?
- Is fallback behavior defined?
- Is model routing explainable?
- Are privacy notes included?
- Are cost/rate-limit notes included where relevant?
- Is human supervision preserved?
- Are outputs verifiable or honestly marked unverified?

## Security Checklist

- No real API keys.
- No real tokens.
- No private keys.
- No production credentials.
- No private hostnames.
- No real SSH hosts unless explicitly public-safe.
- No sensitive personal data.
- No secret values printed in logs or reports.
- `.env.example` only contains placeholders.
- Sample profiles are clearly marked sample/demo.
- Destructive commands require human review.
- MCP permissions are documented.
- Dependency risks are considered.

## Accessibility Checklist

- Every interactive element has an accessible name.
- Icon-only controls include labels.
- Keyboard navigation is preserved where applicable.
- Focus states are visible or logically clear.
- Color is not the only state indicator.
- Contrast is sufficient.
- Motion is not required for comprehension.
- Reduced-motion preferences are respected where possible.
- Text remains readable.
- Touch targets are practical on mobile surfaces.

## Performance Checklist

- Does the change avoid unnecessary JavaScript?
- Does the change avoid heavy dependencies?
- Are assets optimized?
- Is lazy loading considered where useful?
- Are animations performance-safe?
- Does the change avoid blocking startup unnecessarily?
- Does the change preserve mobile performance?
- Does the change consider Apple Silicon and battery where relevant?
- Does the change reduce rather than increase long-term performance risk?

## Documentation Checklist

- Is the purpose clear?
- Is status clear: planned, demo, prototype, experimental, stable, deprecated, or removed?
- Are setup instructions accurate?
- Are demo/live boundaries documented?
- Are security boundaries documented?
- Are future extensions documented?
- Are known limitations listed?
- Are next steps listed?
- Is the document public-safe?
- Is the document useful to both humans and AI agents?

## GitHub Checklist

- Is the change reviewable?
- Is the branch focused?
- Is the PR title precise?
- Is the PR body complete?
- Were available checks run?
- Are failures reported honestly?
- Are risks documented?
- Is rollback clear?
- Are issue/PR templates respected?
- Does the repository remain public-ready?

# Appendix L — Extended Role Protocols

## Lead Architect Agent Protocol

The Lead Architect Agent must always begin by understanding the current repository state. It must never assume that previous plans were implemented. It must inspect first, define the smallest safe scope, coordinate specialists, protect the web demo, protect Apple-first direction, protect public/private boundaries, and produce an honest final report.

The Lead Architect should ask internally:

- What is the highest-value safe improvement?
- What is risky?
- What can be verified now?
- What must be deferred?
- What should become an ADR?
- What belongs in SEIS Brain?
- What improves Apple-first direction?
- What prevents generic SaaS drift?

## Swift Agent Protocol

The Swift Agent improves native foundation. It creates only meaningful Swift code. It may define models, tokens, packages, tests, metadata, and reusable components. It must avoid symbolic Swift files, fake native folders, unused placeholders, and Apple cosplay.

## AI Core Agent Protocol

# Appendix S — Anti-Drift Rules

SEIS must resist drift. Drift occurs when small changes gradually weaken identity, architecture, documentation, or safety.

## Generic Product Drift

Reject changes that make SEIS look like a generic SaaS dashboard, admin template, portfolio, random AI wrapper, or fake macOS clone.

## Web-first Drift

Reject changes that make JavaScript or TypeScript the long-term architectural center. Web remains a demo and public showcase. Apple native remains the destination.

## Fake AI Drift

Reject demo code that claims to be live AI. Reject provider integrations that expose keys in public code. Reject AI output that claims verification without executing checks.

## Documentation Drift

Reject documentation that describes planned features as stable. Mark status clearly. Update docs when code changes.

## Security Drift

Reject real credentials, private keys, private hostnames, unsafe SSH commands, exposed tokens, and unsafe MCP assumptions.

## Design Drift

Reject decorative icon noise, inconsistent typography, messy spacing, low contrast, excessive glassmorphism, and visual patterns that do not feel like SEIS.

## Architecture Drift

Reject duplicated responsibilities, hidden dependencies, giant files, premature distributed systems, and framework churn.

## Repository Drift

Reject large undocumented commits, unclear branch names, broken demos, stale README, missing templates, and ignored failed checks.

# Appendix U — Detailed Platform Standards

This appendix defines operational standards for future platform work. It is intentionally practical so agents can convert broad principles into concrete engineering behavior.

## Web Demo Standard

The web demo exists to communicate the SEIS vision publicly. It should remain fast, accessible, responsive, and no-key. The web demo should not become the long-term center of the architecture. It should not hide broken features behind fake interactivity. It should clearly label demo states, planned states, unavailable states, and live states.

A web demo improvement is valid when it improves clarity, presentation, accessibility, performance, public readiness, or user understanding. A web demo improvement is invalid when it adds visual noise, fake AI, unnecessary dependencies, broken navigation, or generic dashboard patterns.

## macOS Standard

macOS is the long-term flagship native platform. Future macOS work should prioritize Swift packages, SwiftUI surfaces, native accessibility, command center workflows, provider visibility, SEIS Brain access, safe SEIS-SSH metadata, GitHub/CI visibility, and local AI status. macOS work must remain modular and must not copy Apple apps.

## iPadOS Standard

iPadOS is the long-term review and knowledge surface. It should support SEIS Brain browsing, roadmap review, design review, prompt library review, context pack reading, and creative planning. It should respect touch, Pencil, and tablet ergonomics instead of forcing desktop workflows into a tablet shell.

## iOS Standard

iOS is the companion surface. It should support quick status, agent reports, GitHub/CI glance, SEIS Brain search, notes, provider status, and safe notifications. It should not become a crowded engineering IDE.

## visionOS Standard

visionOS remains research until Apple-first foundations are healthy. Potential value includes spatial architecture maps, knowledge graph exploration, design reviews, research demos, and immersive command center concepts. Never implement visionOS for novelty alone.

## Swift Package Standard

A Swift package is valid when it provides reusable models, architecture, components, utilities, tokens, metadata, tests, or validation. A Swift package is invalid when it only exists for symbolic language statistics.

Each Swift package should document purpose, modules, public interfaces, tests, roadmap, and examples. It should compile when tooling is available.

## AI Provider Standard

A provider integration is valid when it is modular, documented, secure, backend-isolated where required, tested or mock-tested, and clearly separated from demo mode. A provider integration is invalid when credentials are placed in frontend code, demo responses are presented as live, errors are hidden, or provider assumptions are hard-coded.

## MCP Standard

An MCP is valid when its source is evaluated, permissions are documented, secrets are protected, risks are classified, and SEIS value is clear. An MCP is invalid when installed blindly, undocumented, over-permissioned, or unsafe for public repo usage.

## Documentation Standard

Documentation should reduce uncertainty. It should not inflate the repository with repetitive filler. Every document should make a future task easier, safer, clearer, or more maintainable.

## Education Standard

Educational content should help designers become more engineering-aware and engineers become more design-aware. It should include practical workflows, examples, architecture reasoning, and common mistakes.

## Research Standard

Research must be honest. Research findings may guide roadmap and architecture, but they must not be presented as working product. Research should be captured in SEIS Brain, docs, or ADRs when important.
